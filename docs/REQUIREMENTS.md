## 0. 給 AI 的協作規則（必讀）

1. **`Allocate`（第 8.1 節分層比例分配器）由使用者親手實作。** AI 只定介面、方法內容丟 `NotImplementedException`，不得撰寫或補完實作。使用者卡住詢問時，只給提示與方向，不給完整程式碼。
2. **所有黃金情境（第 23 節）的預期值由使用者親手計算。** AI 只能建立表格式測試的骨架（情境名稱、輸入欄、說明欄），預期值欄留空。AI 不得自行填入或修改預期值。理由：實作與測試若出自同一個 AI，可能共用同一套錯誤理解，導致測試全綠、數字全錯。
3. 測試與規格對不上時，先回報「是程式錯，還是規則沒想清楚」，不得自行修改規則或測試來讓它通過。
4. 動手改現有程式前，先讀相關檔案並說明現況（例如 `PeriodService` 現在怎麼產生起訖日）。
5. 新增或修改資料結構時，必須符合第 2 節的核心原則；違反時先提出，不得默默繞過。
6. 金額運算一律使用 `decimal`，不得使用 `double`／`float`。

## 1. 產品定位

- **要解決**：每月預算控制；把每天的手動輸入降到最低。
- **不解決**：記帳本身的麻煩。產品不假裝能消掉它。
- **核心機制：例外回報**。預算事先切成時段與類別；沒回報就視為照預算花掉，只有花多、花少才回報。
- **差異化**：
  - 例外回報與時段（餐別）預算，現有記帳 App 未見。
  - 不串接銀行帳號、不取得銀行資料。資安是定位優勢，所有功能不得破壞這一點。

## 2. 核心原則（全系統適用）

### 2.1 保守原則
對不確定的事保守，對確定的事誠實，並讓「確定」的代價越低越好。

- 高估可用金額的代價大於低估，未知一律往保守算。
- 只有未知部分保守；已確認的部分照實呈現。
- 首頁同時顯示兩個數字：**今天確定可用**、**待確認的可能結餘**（例：+120，確認後才轉為可用）。
- 釋出的錢不自動變成花費額度；不夠的錢不自動從存款扣。

### 2.2 存事實，數字由重播計算
- 資料庫只存「發生的事實」與「設定」，衍生數字（差額、結餘、每日額度）一律由 `BudgetEngine` 重播時計算，不落地儲存。
- 事實只新增、不覆寫。修正以新事件表達，並標明取代哪一筆。

### 2.3 設定與事實分開（見第 4 節）
- 設定帶生效日、存成版本，不能回溯改變過去。
- 事實可以補登到過去。

### 2.4 隱私
- 不上傳消費資料給第三方；任何統計上傳預設關閉、選擇加入，只傳不含金額的比例資料。

## 3. 基礎定義（最先實作）

實作順序：**邏輯日 → 期間 → 設定版本化**，三者同一次定案，之後才寫黃金情境預期值。

### 3.1 邏輯日
- 一天的起點是可設定的時間（例如 04:00），不是午夜。**［未定］預設值。**
- 全系統凡是用到「哪一天」都依邏輯日判斷：星期幾、平日或假日、國定假日、期間歸屬、今日額度換日。
  - 週六 01:00 的消費屬於週五，套平日預算。
  - 發薪首日 02:00 的消費屬於上一期最後一天。
- 邏輯日起點本身是設定，適用第 4 節版本化。

### 3.2 時段
- 時段必須完整切分 24 小時，不得有空隙或重疊。**［未定］做法：時段邊界互相銜接（例：午餐 10:30～16:00、晚餐 16:00～隔日 04:00），或另設「時段外」預設歸屬。**
- 用途：發票時間對時段、未回報時段卡。

### 3.3 時間與時區
- 事實的發生時間存 UTC＋當地時區；邏輯日依當地時間計算（支援旅遊，第 17 節）。
- 發票時間為台灣當地時間、無時區，匯入時補上 `Asia/Taipei`。
- 事實另存登錄時間（何時記進系統），用於重現「截至某時間點系統算出的結果」與修改紀錄。

### 3.4 期間與發薪日
- 期間存明確起訖日期；程式不寫死每月幾號。
- 下一期起點規則為可設定項：
  - 固定日期（每月 X 號）。
  - 遇假日：往前推、往後推、不調整。
  - 以工作日或銀行營業日為準。
- 範例規則：5 號當天或往前推的最後一個工作日（5 號週六→4 號；週日→3 號；連假中→連假前最後一個工作日）。
- 使用者可手動覆蓋實際入帳日。
- 非固定收入：用日曆月或自訂起始日。
- 已開始的期間，起訖日不因規則變更而改變；新規則從下一期生效。
- 報表兩種視角：依期間（月結）、依日曆月（對照信用卡帳單與發票）。

### 3.5 假日行事曆
- 每年從政府資料開放平台匯入一次國定假日。
- 補班日算平日；國定假日算假日。
- 發薪日規則、餐費平日／假日天數共用同一份行事曆。
- `PeriodService` 需提供「本期平日天數／假日天數」。

## 4. 設定版本化與事實

### 4.1 設定
- 所有預算設定（金額、比例、權重、鎖定、發薪規則、邏輯日起點）帶生效日，存成版本。例：「9/1 起午餐 150」「9/15 起午餐 180」。
- 重播時，每一天套用當天有效的版本。
- 一般設定頁的生效日不得早於今天；要改過去須走「更正」流程並留紀錄。
- 當天修改預設從明天生效。**［未定］今天尚未回報的時段是否套新值。**
- 自動分配模式下期中修改：以「期間總額－已發生部分」對剩餘天數重算，不是新單價乘全期天數。手動模式改完超過剩餘額度，走超支規則。

### 4.2 事實
- 回報、發票、對帳餘額、收入、轉帳皆為事實，存發生時間與登錄時間，可補登到過去。
- 補登到已月結的期間：快照不改，以調整項進當期並標明來源期間。**［未定］細節與月結規格一起定。**

### 4.3 重播範圍
- 只重播當期（第 21 節效能）。每期期初的起始狀態＝上期快照結轉值＋當時有效的設定版本。

## 5. 帳戶模型

### 5.1 多帳戶與現金
- 帳戶類型：銀行（可多個）、現金、電子支付儲值（悠遊卡、LINE Pay 等）、信用卡。
- 帳戶之間互轉不算花費。

### 5.2 信用卡（負債帳戶）
- 刷卡：花費照常扣預算，同時信用卡負債增加。
- 繳卡費：銀行減少、負債減少，不扣預算。
- 對帳用的實際餘額＝各資產帳戶加總－信用卡負債。

### 5.3 資產與負債類事實
- 應收（代墊，第 13 節）、應付、分期負債、預留款皆屬資產負債面，不影響預算。

## 6. 預算結構

- 收入 → 分層分配（第 8 節）→ 花費類別進每日引擎；儲蓄進目標罐子（第 11 節）。兩條路徑在資料模型中分開。
- 花費類別分兩種：
  - **時段預算**：餐費依早午晚、平日假日切分，每日有額度。
  - **月類別預算**：娛樂、交通等，只有期間總額。
- 固定支出：房租、電信、訂閱、分期等，以固定金額鎖在每期預算。

---

## 7. 依 % 分配（大區塊）

- 每個區塊（類別、儲蓄）有「用 % 計算」勾選；未勾即固定金額。
- % 算在扣掉固定支出之後的餘額上。例：收入 40,000、房租固定 12,000，餘 28,000 照 % 分。
- % 總和不得超過 100%；設定頁即時顯示「已分配 85%，剩 15% 進待分配池」。
- 區塊可設底線；錢不夠時處理方式見第 8.1 節。
- 零頭：最大餘額法，加總等於可分配金額。
- 月中進來的收入不自動重算本期每日額度，使用者可手動撥進待分配池。
- **［傾向］** 非固定收入的 % 基準：上期實際收入。

## 8. 分配器與餐費設定

### 8.1 分層比例分配器（`Allocate`，使用者親手實作）

用於三處：餐費分早午晚、範本套用分大區塊、微調重算。

**輸入**：總額、格子清單、取整單位。
每一格包含：
- 鍵值
- 天數
- 權重
- 鎖定的單價（可空）
- 底線（可空）
- 層級（數字越小越晚被擠壓；單層場景全部填同值）

另需一個參數：釋出份額的接收格子（可空）。

**輸出**：每格單價（`UnitAmount`，每餐／每次的金額，不是每日）、零頭（進待分配池）、`Errors`、`Warnings`。`Errors` 非空時不回傳分配結果。

**演算法**：
1. 排除天數為 0 的格子。
2. 鎖定先扣：鎖定合計＝各鎖定格單價 × 天數。剩餘可分＝總額－鎖定合計；小於 0 → 錯誤「鎖定的金額已超過預算」。
3. 權重合計（權重 × 天數）為 0 → 錯誤。
4. 未鎖定格照權重分：單價＝剩餘可分 × 權重 ÷ Σ(未鎖定格權重 × 天數)。
5. 每格無條件捨去到取整單位。
6. 零頭依小數部分由大到小，逐格加一個取整單位，前提是零頭 ≥ 取整單位 × 該格天數；不夠就跳過看下一格。同分依輸入順序決勝。
7. 剩下的零頭進待分配池。
8. 底線：任一格低於底線 → 固定在底線、視為鎖定、從分母移除，整輪重算，直到沒有格子低於底線。鎖定合計＋底線合計 > 總額 → 錯誤。
9. 分層：差額（被擠壓的份額）由層級高者先吸收；下一層可分的是上一層分完後剩下的錢。
10. 釋出份額（未勾選或鎖定值低於範本份額）導向接收格子（通常為儲蓄）。

**不變量**（每個測試都要斷言）：
1. Σ(單價 × 天數)＋零頭＝總額。
2. 鎖定格輸出＝鎖定值。
3. 每格單價 ≥ 底線，否則必有錯誤。
4. 每格單價為取整單位的整數倍。
5. 相同輸入跑兩次結果完全相同。
6. 零頭 < 任一可加格（取整單位 × 天數）的最小值。

**開發步驟**：單層無底線（通過 12,000 範例）→ 天數 0 排除 → 底線夾住重算 → 錯誤處理 → 分層與釋出份額。需要改介面時，先改介面再寫實作，不在函式內寫特例。

**介面草稿**：

```csharp
public record AllocationCell(
    string Key,
    int Days,
    decimal Weight,
    decimal? LockedUnitAmount,
    decimal? Floor,
    int Tier);

public record AllocationResult(

    decimal Leftover,
    IReadOnlyList<string> Errors,
    IReadOnlyList<string> Warnings);

public static AllocationResult Allocate(
    decimal budget,
    IReadOnlyList<AllocationCell> cells,
    decimal roundingUnit,
    string? releasedShareReceiverKey = null)
    => throw new NotImplementedException();
```

實作完成後，由使用者自己寫一段演算法說明。

### 8.2 餐費設定畫面

**問題**：% 算出的餐費總額，與「平日／假日 × 早午晚 × 天數」的逐格金額，要靠手算對齊。

**兩種模式，同一張表切換**：
- **自己設定**：直接填每格金額。超過預算時擋住儲存，不只變紅。
- **自動分配**：設權重（例：早：午：晚＝1：2：2，假日 ×1.2）、鎖定、取整單位、底線，由分配器算出金額。

**即時合計（兩模式皆有，最先做）**：
- 平日（早＋午＋晚）× 平日天數＝小計
- 假日（早＋午＋晚）× 假日天數＝小計
- 合計／餐費預算，顯示剩餘或超出；超出變紅。

**模式切換**：
- 自己設定 → 自動分配：以目前金額反推權重（每格金額 ÷ 基準格金額），切換當下數字不跳。
- 自動分配 → 自己設定：保留算出的金額當起點，解除所有鎖定。

**微調（＋／－按鈕）**：
- 按下後，以「原值 ± 調整量」重算，其他未鎖定格自動吸收，合計不超過預算。
- 確認後，把新金額反推為新權重（新權重＝新金額 ÷ 每單位權重），不留下鎖定；鎖定只保留使用者明確設定的。
- 畫面顯示其他格的實際變化量（重算前後相減，不用比例推估；重新取整後某格可能不降反升）。
- 按鈕旁顯示總額變化（平日 +10 需挪 220，假日 +10 需挪 80）。

**每期天數不同**：固定的是餐費總額，每餐金額每期重算。

**零頭來源**：大區塊 % 分配與餐費分配各產生一次零頭，進待分配池時記錄來源層。

**期初設定值與期中調整值分開存**：超支攤提、護欄只調整每日額度，不回頭改這張表。

## 9. 每日運作

### 9.1 今日額度
- 首頁：今天確定可用、待確認可能結餘。
- 換日依邏輯日。

### 9.2 滑卡確認
每日回報統一成卡片疊：發票卡、未回報時段卡、對帳差額卡，共用同一套手勢。

| 手勢 | 意義 |
|---|---|
| 右滑 | 確認系統猜測（例：12:30 便當 80 → 午餐）；未回報時段卡＝照預算 |
| 左滑 | 修正：選時段或類別、調整金額；修正後系統記住該品名 |
| 上滑 | 不算我的（代買、可報帳、之後會收回） |

防呆：
- 滑完底部顯示「已扣午餐 80 ［復原］」數秒。
- 拖動時卡片邊緣先浮出結果（「→ 午餐」「改分類」）。
- 滑過卡片寬度三到四成才算數。
- 上方「全部照猜測確認」可批次處理。
- 卡片與螢幕邊緣留距離，避免與 iOS 邊緣返回手勢衝突。
- 方向最多三個。

實作：卡片元件（位移、旋轉、放手判斷、回彈、復原）；以 iPhone 實機從主畫面開 PWA 測手勢。

### 9.3 全天例外
- 一鍵「今天全部 0」（在家吃、斷食、有人請客）。
- 一鍵「今天全部照預算」。

### 9.4 通知
- 每晚一則，點開即當天卡片疊，目標五秒內滑完。
- 一天最多一則；超支、中獎、發薪等集中併入晚上那則。月結依第 12 節另行觸發。
- 推播之後才發生的消費（宵夜），在隔天卡片疊出現，並可確認到前一個邏輯日。
- 未確認的時段照預算計算（保守）。

## 10. 超支處理

### 10.1 基本規則
- 超支從剩餘天數平均扣。
- 攤回之前先預覽（`ImpactPreview.vue`）：「接下來 16 天每天少 75，確認嗎？」
- **［未定］** 超支攤提是否共用分配器（每天當一格、天數 1、權重 1、取整 1）。

### 10.2 超支螺旋護欄
- 每日額度只扣到某個下限，超過下限的部分延到下一期，或從待分配池、儲蓄目標扣。
- 超支太大時，讓使用者選擇：本期慢慢還、分兩期還、直接從存款吸收。
- **［未定］** 下限的預設值與觸發門檻。

## 11. 待分配池與罐子

### 11.1 待分配池
- 來源：時段省下的錢、對帳正差額、發票中獎（入帳後）、分配零頭、手動撥入的月中收入。
- 不直接加到每日額度。

### 11.2 罐子（統一機制）
預約支出、年繳預留款、儲蓄目標，都是「有目標金額與到期日的罐子」。

- **預約支出**：例「10/20 紅包 3,600」。登記當下即從「確定可用」扣除預留額；池子不夠時攤到每日額度。到期時實際金額與預留的差額，走超支或結餘規則。
- **年繳**：每期提撥 1/12 進預留款，到期從預留款付。
- **儲蓄目標**：旅遊基金、緊急預備金等。

**分配順序**：
1. 有到期日且快到期者優先（預約、年繳）。
2. 其餘依使用者設定的比例或上限。
3. 可設自動規則，例：省下的一半自動轉入儲蓄目標。

## 12. 對帳與月結

### 12.1 對帳（用實際餘額補回沒回報的期間）
- 存「那天的實際餘額」（第 5 節定義的淨額），不存差額。
- 重播到對帳日時，算出預期餘額並與實際比，差額為「沒交代的差異」，攤到之後的天數。
- 之後補回報該期間的事實，重播時差額自動縮小，不重複扣。
  - 例：對帳差 -1,200，補回報聚餐 1,000 → 沒交代的差異變 200，總扣款仍 1,200。
- 歸因前先扣掉已知非日常項目：薪水入帳、固定支出、帳戶互轉、繳卡費、投資買賣、應收應付變動。
- 負差額（花多了）：走超支規則。正差額（省了）：進待分配池。
- 攤回前預覽；差額超過月預算一定比例（例 30%）時，先詢問是否漏記大額或固定支出，並提供拆出單獨記錄的入口。

### 12.2 月結（發薪前）
1. 上一期沒結，這一期預算不能正式啟用。
2. 月結先對一次帳（輸入發薪前實際餘額）。
3. 報表三到五個重點：
   - 本期省或超多少，與上期比。
   - 最常超支的時段或類別（例：午餐 12 天超預算）。
   - 細項中超最多的。
   - 沒交代的差異金額。
   - 目標進度與預計達成日。
4. 最後一步做決定：下期是否調整（例：午餐 150 → 180），確認後才算完成。此步驟同時提示「實際花費與預算的差距」，比較對象為使用者自己的預算，在本機計算。
5. 存成不可修改的快照：當期結果、對帳餘額、做了哪些調整。
6. 完成時顯示結果：「上期省了 2,300，已放進待分配池」。

## 13. 類別細項

- 月類別預算只有總額，超標時看不出是哪一項。
- 回報可標細項：娛樂費 → 電影 350。
- 細項可選擇性設上限（例：遊戲每月最多 500）。
- 月結或超標時看得到是哪個細項。
- 超出部分照現有規則從待分配池扣。
- 記帳是可選的放大鏡，平常照預算不用記。
- 實作前先讀 `EntryService`、`LedgerView` 確認現況；細項層加在不影響 `BudgetEngine` 重播邏輯的位置。

## 14. 共用支出（分帳）

代墊的錢不是花費，是應收款（資產）。

- 例：晚餐 800 我全付、兩人平分：我的 400 扣晚餐時段預算；多付的 400 記「應收：小明 400」，不影響預算；還錢時應收清掉、銀行 +400，預算不動。
- 別人先幫我付：應付款（負債）。我的份照扣預算，還錢時從帳上扣。
- 對帳時系統辨識應收應付，不誤判為沒交代的差異。
- 第一版：分帳對象只是名字。
- 第二版：分享連結，對方不需註冊，可按「我已還款」。
- 加好友最後做（權限、衝突、通知、隱私成本高）。

## 15. 分期與年繳

- 兩種輸入模式：
  - 簡易：每月 X 元、共 N 期。
  - 細部：本金、利率、期數、手續費；可表達 0 利率含手續費。
- 分期：每期繳款＝固定支出；負債逐期減少。
- 年繳：見第 11.2 節。
- 提前還款：從資產支付，負債減少，不算花費、不扣預算；使用者選擇每期金額變少（期數不變）或期數變短（金額不變）。
- 還款來源可為存款加部分月薪。

## 19. 發票載具串接與對獎（載具辦好並自用一個月後再定規則）

### 19.1 串接
- 走財政部電子發票 API 正式申請，不自行抓取。
- 時間 → 時段（依邏輯日與時段定義）。
- 品名關鍵字 → 類別（便當、麵、飯糰 → 餐費；飲料 → 飲料）。
- 自動比對實際金額與時段預算，產生待確認卡。
- 發票不自動關閉時段，只有使用者確認才關閉：
  - 發票進來：顯示「已知 80，預算 200」，時段＝待確認。
  - 確認：實際 80，省下 120 進待分配池。
  - 補一筆無發票 +50：實際 130。
  - 未處理：照預設 200 計算。
- 一張發票多品項：依品名拆到不同類別；未命中關鍵字的品項有預設歸屬。
- 修正即學習：改一次「飯糰 → 早餐」，之後自動猜對。關鍵字表初始手動設定。
- 消費時間 ≠ 用途時間（晚上買隔天早餐）：以左滑修正處理。

### 19.2 對獎
- 政府已自動對獎並匯入領獎帳戶；App 只需知道中獎並記入模型。
- 每期開獎後比對 API 取得的發票號碼。
- 中獎跳卡片：「9-10 月發票中 200 元」。
- 先標「待入帳」，實際入帳或手動確認後才轉入待分配池。
- 大獎以實際入帳金額為準；扣稅門檻與稅率實作前查財政部現行規定。

## 20. 前期設定、範本與引導

### 20.1 原則
- 設定在使用過程中逐步長出來，不一次問完。
- 目標：一分鐘內看到「今天可花 X」。
- 延後詢問：
  - 固定支出：第一次對帳有差額時。
  - 時段比例：用一週後依實際回報建議。
  - 載具：養成每日確認習慣後。
  - 資產與目標：第一次月結後。

### 20.2 第一個問題
- **［傾向］** 問月收入（範本的房租、儲蓄 % 以收入為基準），由範本算出「可花」。非固定收入者問上期實際收入。

### 20.3 範本挑選
- 以三個問題決定範本，放在同一畫面、點選作答：
  1. 住家裡或在外租屋。
  2. 大多外食或自己煮。
  3. 住雙北或其他縣市。
- 組合對應範本，例：「雙北租屋外食上班族」。使用者不需懂 631 或 50/30/20。

### 20.4 範本內容
- 大區塊 %：房租、餐費、交通、娛樂、儲蓄、保險。
- 餐費權重：早：午：晚、假日倍率（分配器初始權重）。
- 常見固定支出項目名稱：房租、電信、訂閱（金額留空）。
- 「住家裡」範本：房租改為可選的孝親費或移除，不顯示 0%。
- 每組 % 的推導過程寫入設計筆記。

### 20.5 套用畫面（預覽即第一次看到今日額度）

```
套用範本：雙北租屋外食　　月收入 40,000

[✓] 房租      25%   實際金額 [12,000]  ← 填了就鎖定
[✓] 餐費      25%
[✓] 交通       8%
[ ] 保險      10%   ← 沒勾：我沒有
[✓] 娛樂      10%
[✓] 儲蓄      22%
```

規則：
1. 勾選的項目才套用。
2. 填了實際金額即鎖定並先扣，範本 % 作廢。填了金額的項目轉為固定支出；套用後依第 7 節，% 只算在扣掉固定支出之後的餘額上。
3. 未勾選＝鎖定在 0。
4. **釋出份額**（未勾選，或鎖定值低於範本份額）：進儲蓄（預設，使用者可改）。
5. **被擠壓份額**（鎖定值高於範本份額）：儲蓄為受保護層，最後才動；先由娛樂、交通、餐費等一般層依權重吸收。可設儲蓄最低比例（即底線）。
6. 底線照第 8.1 節夾住重算；固定金額加總超過收入、或鎖定＋底線超過收入時報錯。
7. 預覽顯示實際金額，並標出調整來源。基準為「套用勾選後、套用鎖定前」的金額，數字為實際重算的前後差。
   - 例：房租 15,000 高於範本 10,000，儲蓄受保護不動，5,000 依 25：8：10 分攤 → 餐費 -2,907、交通 -930、娛樂 -1,163。
8. 每項旁同時顯示範本 % 與調整後占收入 %（例：儲蓄 22% → 32%）。
9. 保險勾選框旁提示：年繳保費應走預付提撥，不是取消勾選。
10. 預覽中的餐費每餐金額，由分配器依當期實際平日／假日天數算出，不用固定 22／8 天估計。

### 20.6 套用後
- 複製，不連結：範本值複製為使用者設定，之後與範本無關；範本更新不影響已套用者。
- 記錄套用的範本代號與版本，並保存當時的值作為快照。

### 20.7 出處與免責
- 標示來源時照實區分：631、50/30/20 標「常見理財法則」；主計總處家庭收支調查只標它實際支撐的數字。
- 附註：「僅供起點參考，請依個人狀況調整」。

### 20.8 範本改進
- 統計上傳：預設關閉、選擇加入；只傳範本代號與各區塊調整比例，不傳金額；同一範本累積足夠人數才納入；隱私說明逐項列出。
- 某區塊調整幅度分散大者，改為引導時直接詢問，而非調整平均值。

### 20.9 引導
- 唯一一開始必須教會的概念：**沒回報＝照預算花；省下的錢要回報才算數**。
- 流程：回答三題並輸入收入 → 範本預覽（看到今天可花）→ 滑一張示範超支卡，看到額度自動調整 → 看一張未回報時段的說明 → 清除示範資料，開始使用。
- 其他概念出現時才教，每個提示只出現一次：第一次省錢（待分配池）、第一次超支（攤到哪幾餐）、第一次對帳。
- 找沒聽過解釋的人實測，旁觀不開口，記錄卡住處。

### 20.10 中途開始使用
- 第一期範圍＝開始日至期末；金額以使用者輸入為準，按比例折算只作預設建議值。
- 確認 `AddProfileStartDate` 的邏輯與此一致。
